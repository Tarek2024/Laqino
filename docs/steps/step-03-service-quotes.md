# الخطوة 3 — عروض أسعار الخدمات (توزيع، رد المقدم، اعتماد الإدارة، اختيار العميل) + حالة «متنازع عليه»

**الأساس:** الخطوة 2 (`phase-09s2`، كاش v42). **الناتج:** VERSION = `phase-09s3`، كاش `laqino-v43`.

## كيف يعمل (قرارات اتُّخذت لأنها لم تكن مكتوبة)
المسار القديم «مقدم يقبل الطلب مباشرة» **باقٍ كما هو** لطلب في حالة `open`. العميل يختار بنفسه مسار العروض:

`open` → (العميل: «اطلب عروض أسعار») `awaiting_quotes` → (الإدارة تعتمد أول عرض) `quotes_received` → (العميل يختار عرضًا) `provider_selected` → (المقدم المختار يؤكد) `accepted` → ... كما في الخطوة 2.

1. **التوزيع:** العميل يختار من قائمة المقدمين المطابقين (نفس النوع والمنطقة، منشورون، **ولهم حساب** لأن مقدمًا بلا حساب لا يستطيع الرد، وليس حساب العميل نفسه). حتى 10 مقدمين (`MAX_INVITES`). بلا اختيار صريح عبر API يُدعى أول 10. يصل المدعوين إشعار.
2. **رد المقدم:** المدعو فقط يقدّم عرضًا (سعر 1..1,000,000 ج + ملاحظة حتى 300 حرف). عرض واحد لكل مقدم لكل طلب. تعديل العرض يعيده «بانتظار الاعتماد». له سحبه قبل الاختيار. **ممنوع رقم هاتف في الملاحظة** (8 أرقام متتالية فأكثر، بما فيها الأرقام العربية والمسافات) حتى لا يتجاوز المنصة.
3. **اعتماد الإدارة:** كل عرض يبدأ `pending` ولا يراه العميل. الإدارة تعتمد (`approved`) أو ترفض مع سبب إلزامي (`rejected`، يظهر للمقدم وله إعادة التقديم). الاعتماد ينقل الطلب إلى `quotes_received` ويُشعِر العميل. سحب/رفض آخر عرض معتمد يرجّعه `awaiting_quotes`.
4. **اختيار العميل:** يرى العروض المعتمدة فقط (الأرخص أولًا، بلا أي رقم هاتف) ويختار واحدًا ← `provider_selected`. **المقدم المختار لا يرى بيانات العميل (رقم/عنوان/صور) إلا بعد أن يؤكد.**
5. **تأكيد المقدم:** «أكّد القبول» ← `accepted` وتنكشف بيانات العميل، وباقي العروض تصير `not_selected` ويُبلَّغ أصحابها. «اعتذر» أو انتهاء مهلة `SELECT_TTL_DAYS` (يومان، كسولة كالانتهاء الآخر) أو فك ربط الحساب: العرض المختار يصير `withdrawn` ويرجع الطلب لمرحلة العروض وباقي العروض المعتمدة تبقى قائمة للعميل.
6. **النزاع (`disputed`):** العميل أو المقدم يفتح نزاعًا بسبب (10..300 حرف) على طلب `accepted/on_the_way/in_progress` أو `done` خلال `DISPUTE_WINDOW_DAYS` (7 أيام). مرة واحدة لكل طلب. تُشعَر الإدارة والطرف الآخر. الإدارة تحسمه بـ`done` أو `cancelled` مع سبب إلزامي (5 حروف+) من نفس شاشة طلبات الخدمات. سبب العميل يراه العميل والإدارة فقط، وسبب المقدم يراه المقدم والإدارة فقط. **هذا أدنى حد يفعّل الحالة؛ إدارة النزاعات الكاملة (خدمات + سوق) في الخطوة 6.**

## الترحيل
بلا إعادة بناء للجدول: `ALTER TABLE ... ADD COLUMN` لثلاثة أعمدة + جدولان جديدان، متكرر بأمان واختُبر على قاعدة بصيغة الخطوة 2. **خذ نسخة احتياطية قبل أول تشغيل مع ذلك** (`backup_restore.py`).

## تغيّر سلوك API
- القبول المباشر `…/accept` صار مقصورًا على الطلب `open` (كان يسمح فنيًّا بـ`awaiting_quotes/quotes_received` لكن لم يكن لهما مسار). طلب بنظام العروض يردّ 409 برسالة تدل على تقديم عرض.
- حسم النزاع كان غير ممكن (`disputed` طرفية)؛ صار `done/cancelled` من الإدارة فقط.
- فك ربط حساب مقدم كان يعيد طلباته الجارية إلى `open`؛ ما زال كذلك، ويضاف أن طلبًا «مختارًا لم يؤكد» يرجع لمرحلة العروض.

## لم يُنفَّذ / مخاطر معروفة
- **كل عرض يحتاج اعتماد الإدارة** (طلب المالك): عبء يدوي يكبر مع الحجم؛ لا اعتماد تلقائي ولا صلاحية موظف محددة (الخطوة 6).
- إلغاء العميل أو انتهاء الطلب أثناء مرحلة العروض **لا يُشعِر** المقدمين الذين قدّموا عروضًا (يُبلَّغ فقط من اختير). المدعوون يُحدَّدون وقت الطلب ولا تُعاد الدعوة لاحقًا.
- لا صلاحية لعرض السعر (يبقى حتى اختياره أو إغلاق الطلب)، ولا مقارنة بالميزانية، ولا كشف أرقام داخل نص العنوان أو الصور.
- `overview.py` (لوحة النظرة العامة) لم تُضَف إليها عدّادات العروض/النزاعات؛ تظهر في تبويب طلبات الخدمات وإشعار الإدارة (`admin:svcreq`) فقط.
- حالات الاختيار/النزاع تُفحص كسولًا عند أول طلب API لمسارات الخدمات (لا مؤقّت).
- لم يُجرَّب على هاتف حقيقي.

## الرجوع
أوقف السيرفر واسترجع `svc.py`, `index.html`, `admin.html`, `sw.js` من الخطوة 2. الجدولان والأعمدة الجديدة تبقى بلا أثر. أعد الطلبات العالقة قبل الرجوع (الكود القديم يعرف هذه الحالات لكن بلا مسار يخرجها منها سوى الإلغاء):
`UPDATE service_requests SET status='open', provider_id=NULL WHERE status IN('awaiting_quotes','quotes_received','provider_selected');`
وطلب `disputed` يبقى طرفيًّا في الكود القديم (حلّه قبل الرجوع من الإدارة: `done` أو `cancelled`).

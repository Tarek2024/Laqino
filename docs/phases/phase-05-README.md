# المرحلة 5 — الخدمات المحلية وطلبات العملاء

## 1. الهدف والافتراضات
الدليل (أنواع الخدمات ومقدموها وكشف الرقم) كان موجودًا. أُضيف **طلب الخدمة**: العميل يختار نوعًا ومنطقة ويكتب وصفًا، والإدارة تستلم الطلب وتتابعه، والعميل يرى الحالة.
افتراضات (لم تُحسم في الخطة، فاخترتُ أضيقها وقابلها للتعديل):
- الطلب يصل **للإدارة فقط**؛ مقدمو الخدمة بلا حسابات حتى المرحلة 6 (قرار «مقدم الخدمة كحساب» مفتوح)، فلا يُرسَل لهم شيء.
- لا يُكشف أي رقم هاتف لمقدم خدمة عبر هذه المسارات؛ رقم العميل يراه admin/staff فقط. كشف رقم المقدّم يبقى بمساره القديم وحدّه الساعي.
- نوع الخدمة المتاح للطلب هو ما تعرضه `/api/service-types` للعميل (الأنواع التي لها مقدّم منشور في منطقة مفعّلة).

## 2. ما أُنجز فعليًا
- وحدة `svc.py` (بنمط chat.py، لا تستورد server.py) وجدول `service_requests` بإضافة فقط.
- المسارات: `POST/GET /api/service-requests`، `POST /api/service-requests/<id>/cancel`، `GET /api/admin/service-requests?status=`، `POST /api/admin/service-requests/<id>` (حالة in_progress | done | cancelled + ملاحظة ≤300 حرف).
- القواعد: وصف 10–500 حرف، نوع ومنطقة مفعّلان، 3 طلبات مفتوحة كحد أقصى للمستخدم (429)، 10 طلبات/يوم (429)، الطلب لا يراه إلا صاحبه، الطلب المنتهي (done/cancelled) لا يتغيّر (409)، تسجيل كل إجراء إداري في `audit_log`.
- الإشعارات: كل admin/staff يستلم إشعار «طلب خدمة جديد» (رابط `admin:svcreq`)، والعميل يستلم إشعارًا عند تغيّر الحالة (رابط `svc`).
- الواجهات: `index.html` (تبويب خدمات لاقينو: زر «اطلب خدمة»، نموذج، «طلباتي» مع الإلغاء)، `admin.html` (تبويب «طلبات الخدمات» بالمطابقين من المقدمين وأزرار المتابعة؛ صار عدد الأقسام 20)، `notif.js` (رابط svc)، `sw.js` (كاش v36). كل نص عبر `esc()`.

## 5. لم يُنفَّذ / لم يُجرَّب
- لم يُجرَّب على هاتف/Termux/Docker. واجهة الطلب والتبويب الإداري فُحصا نصيًا فقط (لا اختبار Chromium جديد لهما؛ اختبار الأقسام العشرين في Chromium موجود وناجح).
- لا توجّه تلقائي للطلب لمقدم محدد، ولا ردود/عروض من المقدمين (تحتاج حسابات مقدمين: المرحلة 6).
- لا صور في الطلب، ولا مراسلة بين العميل والإدارة داخل الطلب.
- الأنواع التي لا مقدّم منشور لها لا تظهر في نموذج الطلب.

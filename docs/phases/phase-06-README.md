# المرحلة 6 — مقدم الخدمة كحساب

## 1. القرار والافتراضات
قرار «مقدم الخدمة كحساب» لم يُحسم في الخطة، فاخترتُ أضيق تصميم قابل للتعديل:
- **لا دور جديد في `users`** (قيد CHECK على الدور يحتاج إعادة بناء الجدول). الربط بعمود جديد `service_providers.owner_user_id`؛ الإدارة (المدير فقط) تربط الحساب برقم هاتفه، ولا يُربط حساب إدارة.
- المقدم يرى الطلبات **المفتوحة المطابقة** (نفس النوع والمنطقة لمقدم **منشور**) بلا اسم/رقم العميل. عند **القبول** فقط يظهر له اسم العميل ورقمه.
- العميل يرى **اسم** المقدم القابل فقط، دون أي رقم (كشف رقم المقدم يبقى بمساره القديم وحدّه الساعي).
- التقييمات **لم تُنفَّذ** (مؤجلة؛ هذه المرحلة تغطي الحساب والتوجيه والرد فقط).

## 2. ما أُنجز
- ترحيل تلقائي متكرر بأمان: `service_providers.owner_user_id`، `service_requests.provider_id`، `service_requests.accepted_at` + فهرسان.
- مسارات المقدم: `GET /api/my/service-jobs` (200 فارغة لغير المربوط حتى لا تُسجَّل أخطاء في المتصفح) ، `POST /api/my/service-jobs/<id>/accept|release|done` (403 لغير المربوط في الإجراءات؛ القبول حجز ذري `UPDATE ... WHERE status='open' AND provider_id IS NULL` فيفوز واحد والآخر 409؛ سقف 10 طلبات قيد التنفيذ لكل حساب → 429).
- مسارات الإدارة: `GET/POST /api/admin/service-owners` (ربط/فك بالهاتف؛ فك الربط يعيد طلبات المقدم قيد التنفيذ إلى «مفتوح»).
- الإشعارات: طلب جديد → أصحاب المقدمين المطابقين (رابط `svcjob`)؛ قبول/إرجاع/إنجاز → العميل؛ الربط → صاحب الحساب. كل إجراء في `audit_log`.
- الواجهات: قسم «شغل الخدمات» في حسابي (يظهر للمربوطين فقط)، «قبل الطلب: <اسم>» في طلبات العميل، وصندوق «ربط مقدمي الخدمة بحسابات» أعلى تبويب «طلبات الخدمات» في الإدارة (عدد الأقسام يبقى 20). كاش v37.

## 4. لم يُنفَّذ / لم يُجرَّب
- التقييمات، وتوجيه الطلب لمقدم محدد بعينه (الطلب مفتوح لكل مطابق، وأول قابل يفوز).
- لا إشعار للمقدم إن ألغى العميل طلبًا قُبل؛ لا انتهاء صلاحية للطلبات المفتوحة.
- قسم «شغل الخدمات» فُحص نصيًا وبفحص صياغة JS فقط، دون Chromium أو هاتف.
- لم يُجرَّب على Termux/Docker.

## 5. التطبيق
